1. 적용 대상 및 범위

구분 내용

목적 인적 실수로 인한 고객 데이터 유실 사고 방지

시행 2025년 7월 1일

기준일

주의: 본 매뉴얼은 단순 참고용 기술 가이드가 아니라, 교육 현장에서 참고할 수 있도록 정리한

하는 의무 규정입니다.

아래 사항을 숙지하지 않거나 임의로 절차를 생략할 경우, 고객 데이터

손실·장애·업무 중단 등 심각한 사고로 이어질 수 있으며, 회사 정책에 따라 즉시

보고·조사·재발방지 조치가 시행됩니다.

매뉴얼 위반으로 인해 사고가 발생한 경우 “고의 또는 중대한 과실”로 간주될 수

있으며, 작업자는 업무 배제, 재교육, 현장 투입 제한, 사고 조사 참여 등 회사가 정한

내부 규정에 따라 후속 조치를 받을 수 있습니다.

매뉴얼의 모든 내용은 팀의 기술 숙련도와 상황을 고려해 최소한으로 정의된 필수

안전절차이며, 현장 상황이 특별하거나 긴급하더라도 매뉴얼 생략 또는 단독

판단으로의 절차 변경은 절대 금지됩니다.

해당 매뉴얼은 고객 데이터 보호·회사 신뢰도 유지·기술지원팀 전체의 안전 작업 문화

구축을 위한 핵심 문서임을 다시 한 번 명확히 합니다.

📌 공통 안전 수칙

● lsblk, blkid, mount, df -h 등의 명령어로 디바이스 확인 → 마운트 상태 확인 → 파일시스템 확인

순서로 항상 점검.

스토리지 장치 마운트 시 UUID 기반 식별 방식 사용

리눅스 시스템에서 스토리지 장치 경로를 지정할 때 /dev/sda, /dev/sdb, /dev/nvme0n1 등 장치명 기반

지정 방식은 부팅 시점의 장치 인식 순서나 포트 연결 상태에 따라 변경될 수 있다.

이로 인해 다음과 같은 심각한 사고가 발생할 수 있다:

● 마운트 대상 디스크가 바뀌면서 데이터가 없는 다른 디스크가 /data 또는 /home 등으로 마운트됨

● 장애 조치 또는 재부팅 후 마운트 실패 → 서비스 중단 또는 데이터 접근 불가

● 파티션 포맷 / RAID 재구성 / 스토리지 교체 시 의도하지 않은 디스크에 작업 수행

이러한 위험을 방지하기 위해 모든 스토리지 장치 지정은 UUID 기반으로 수행한다.

📍 UUID 방식 개요

UUID는 파일시스템 생성 시 자동 부여되는 고유 식별 값으로, 디스크 위치/포트/장치명과 관계없이 변경되지

않는다.

운영자 또는 시스템 상태 변화에 의한 변경이 없으므로, 장치 인식이 변동되는 상황에서도 항상 동일한

디스크를 정확하게 지정할 수 있다.

UUID는 아래 명령으로 확인한다:

● blkid

예시 출력:

● /dev/sda4: UUID="18a3480a-8ce7-4a9d-ab24-7b5ea76249a3" TYPE="xfs"

📍 /etc/fstab 적용 예시

🚫 장치명 기반(사용 금지)

Page 7

● /dev/sda4 /data xfs defaults 0 0

⭕ UUID 기반(표준 방식)

● UUID=18a3480a-8ce7-4a9d-ab24-7b5ea76249a3 /data xfs defaults 0 0

※ fstab 기록 시 UUID="값" 형태가 아니라 UUID=값 형태로 입력한다.

📍 운영 적용 절차

단계 작업 내용

1 blkid 명령으로 대상 파티션 UUID 확인

2 UUID 정보 복사 후 fstab 또는 마운트 스크립트에 반영

3 변경 적용 시 mount -a 실행하여 오류 여부 확인

4 변경 작업을 운영 이력에 기록하고, 서비스 영향 여부 검증

📍 기대 효과

● 서버 재부팅 및 스토리지 추가/제거 시 잘못된 디스크 마운트 위험 제거

● 장애 조치 이후 스토리지 자동 마운트의 안정성 확보

● 운영자 실수로 인해 타 디스크를 포맷하거나 RAID 구성하는 사고 예방

● 고객 데이터 저장 영역에 대한 무결성 및 접근 안정성 강화
